# 规划质量评分量表 v1

## 这个 rubric 评什么

符号状态机能客观判定两件事：动作是否可执行、目标是否达成。这两件事代码说了算，不需要模型打分。

但有两件事代码判不了：

1. **步骤是否冗余**：一条能达成目标的路径走了很多冤枉路，状态机照样判成功
2. **路径是否更优**：存在明显更短的等价路径，状态机看不出来

这份 rubric 只用来评这两件代码判不了的事。**能用代码判的绝不交给模型**，这是整个项目的一贯原则。

## 维度一：步骤必要性

判定对象：达成目标所需的动作里，有没有冗余步骤。

| 档 | 标准 | 锚点样例 |
| --- | --- | --- |
| 5 | 每一步都必要，无冗余 | `PickupObject(Apple)` → `GotoLocation(Table)` → `PutObject(Apple, Table)`。三步，缺一不可 |
| 4 | 有一步可省但不影响理解 | 多了一次 `GotoLocation`，比如已在桌前又写一次移动 |
| 3 | 有二到三步冗余，路径绕 | 拿起又放下同一个物体，之后再次拿起 |
| 2 | 冗余明显，路径混乱 | 反复在多个容器间移动，看不出意图 |
| 1 | 大量无意义动作 | 十几个动作里大半与任务无关 |

## 维度二：路径效率

判定对象：与 shortest path 相比，这条路径绕不绕。

| 档 | 标准 | 锚点样例 |
| --- | --- | --- |
| 5 | 与最短路径等长或差一步 | gold 是 5 步，模型输出 5 或 6 步 |
| 4 | 比最短路径多两到三步 | gold 是 5 步，模型输出 7 到 8 步 |
| 3 | 明显绕路但仍能达成 | gold 是 5 步，模型输出 12 步 |
| 2 | 极度绕路 | 反复往返于同一组位置 |
| 1 | 无法判断是否绕路（序列本身不可执行） | 前置条件在中途就断了 |

## 维度三：目标覆盖完整性

判定对象：任务描述里的所有要求是否都被覆盖。状态机只按 `pddl_params` 判定，但人工描述里可能有额外要求（比如"顺便把灯关了"）。

| 档 | 标准 | 锚点样例 |
| --- | --- | --- |
| 5 | 显式与隐含要求全部覆盖 | 任务说"把加热过的面包放到桌上"，序列里既有加热也有放置 |
| 4 | 覆盖了主体要求，漏了次要修饰 | 有放置但没加热 |
| 3 | 覆盖了部分要求 | 只拿了物体没放 |
| 2 | 只覆盖了很小一部分 | 只做了移动 |
| 1 | 与任务无关 | 动作和目标物体对不上 |

## 维度四：可读性

判定对象：动作命名与参数是否规范、能否被下游执行器直接解析。

| 档 | 标准 | 锚点样例 |
| --- | --- | --- |
| 5 | 全部符合 `动作名(参数)` 格式，参数用的是场景里真实存在的名字 | `PutObject(Apple, Table)` |
| 4 | 格式正确但个别参数名与场景略有出入（如大小写） | `PutObject(apple, table)` |
| 3 | 格式基本正确，混有少量解释文字 | 部分行带中文注释 |
| 2 | 格式混乱，需要大量清洗 | 动作名写成自然语言描述 |
| 1 | 完全无法解析 | 输出的是一段散文 |

## 使用方式

Judge 输出 JSON，逐维度打分并给理由：

```json
{
  "steps_necessity": 4,
  "path_efficiency": 5,
  "goal_coverage": 4,
  "readability": 5,
  "reason": "多了一次不必要的移动，其余符合要求"
}
```

**四个维度必须独立打分，不要合成一个总分。** 总分无法定位问题，分维度才能说清楚这个模型是"爱绕路"还是"爱漏步骤"。

## 已知局限

- 锚点样例目前由单人标定，未做多人交叉验证
- 路径效率的判定依赖 gold 长度作为参照，若 gold 本身不是最短路径，这个维度会失真
- 这份 rubric 只在状态机判成功之后才用，判失败的样本不需要打分
