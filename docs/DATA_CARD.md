| 数据 hash | `f029b26d541e618c84f28acc49ef5650`（sha256 前 32 位） |
| 生成方式 | `python scripts/import_alfred.py --per-type 45 --limit-scan 8000`，seed=42 |

---

## 一、这是什么

给模型一个家务任务的自然语言描述和场景物体清单，让它输出符号化的动作序列，再用符号状态机执行这条序列，看最终状态是否达成目标。

数据来自 ALFRED 的高层动作标注，**不含图像、视频和特征**，所以评测不需要 GPU 也不需要仿真器。

## 四、难度校准证据

分层不是拍脑袋定的，有实测数据支撑。用 MiniMax-M3 在 315 条上跑的结果：

| 层 | 成功率 | 95% 置信区间 |
| --- | --- | --- |
| L1 | 77.8% | [68.2%, 85.1%] |
| L2 | 48.1% | [39.9%, 56.5%] |
| L3 | 41.1% | [31.5%, 51.4%] |

**L1 的区间下界 68.2% 高于 L2 的上界 56.5%，区间不重叠。** 这说明分层有效，不是随机波动。

另外用 DeepSeek-V4-Flash 复现了同样的梯度（82% / 59% / 59%），两个模型都表现出难度递增，进一步支持分层的合理性。

## 五、已知偏差（重要，请务必读完）

### 1. 子集分布严重不均，泛化实验样本不足

| 子集 | 条数 |
| --- | --- |
| train | 297 |
| valid_unseen | 12 |
| valid_seen | 6 |

抽样时没有按子集分层，导致 `valid_unseen`（训练中未见过的场景）只有 12 条。

**影响**：想做「见过 vs 没见过场景」的泛化对比，样本量不够，结论不可信。

**如果要修**：改用 `python scripts/import_alfred.py --split valid_unseen` 单独抽一批。

### 2. 能力维度标签区分度弱

「长程多步」这个维度覆盖了 313/315 条（99.5%），几乎等于没有区分。

**原因**：判定条件 `len(high_descs) >= 4` 太宽松。

**影响**：想按能力维度定位模型短板时，这个标签提供不了信息。其他几个维度（状态改变-温度 90 条、切片前置依赖 46 条等）区分度正常。

### 3. 容器信息需要从 gold 动作反推

ALFRED Lite 版的 `object_poses` 只登记可移动物体，微波炉、水槽、冰箱、落地灯这类固定器具不在里面，但 gold 动作会引用它们。

**当前的解法**：从 gold 动作的参数反推补全场景（`evalkit/alfred.py` 的 `_augment_scene`）。

**影响**：这意味着场景信息部分依赖了标准答案。虽然补的是环境本来就有的东西（不是给模型放水），但这个依赖关系必须说明。

### 4. 场景物体名 100% 带哈希后缀

所有 315 条的物体名都是 `类型名_哈希` 格式（如 `Mug_2a940808`），而 gold 动作的参数用的是纯类型名小写（`mug`）。

**处理方式**：`normalize()` 函数做归一化。不做的话全部样本会判成「物体不在场景中」—— 这是开发时踩过的坑。

### 5. gold 序列 85.7% 含 NoOp 占位符

270/315 条的 gold 序列末尾有 `NoOp()`，而模型不会输出它。

**处理方式**：比较前先归一化剥掉。不处理的话「序列精确匹配」恒为 0% —— 这是开发时踩过的另一个坑。

### 7. 状态机不校验移动动作，路径长度指标失真（已实测，未修复）

路径多样性分析（`scripts/analyze_path_diversity.py`）实测发现：

| 模型 | 成功样本 | 走了与 gold 不同的路 | 其中更短的 | 更短里靠减少移动的 |
| --- | --- | --- | --- | --- |
| MiniMax-M3 | 172 | 153（89.0%） | 85 | 80（**94%**） |
| DeepSeek-V4-Flash | 207 | 173（83.6%） | 88 | 81（**92%**） |

**原因**：状态机只对 Clean/Heat/Cool 要求站在对应器具前，`PickupObject` 和 `PutObject` 完全不看位置。所以模型不写 `GotoLocation` 也能判成功。

**影响**

- 「路径效率」以 gold 长度为基准会**双向失真**：gold 不是最短路径，而模型那 94% 的「更短」也不是找到捷径，是省略了物理上必须的步骤
- 部分成功率可能被高估——省略移动在真实机器人上做不到

**修复尝试（2026-09-27）**

给 Pickup/Put 补上位置校验后，gold 通过率从 98.7% 掉到 **67.9%**，被 95% 门槛拦住。原因是 ALFRED 的 `GotoLocation` 目标可以是**物体本身**（`GotoLocation(bread)` 走到面包前）而不只是容器，按「必须站在物体所在容器前」校验过严。

**正确修法**：先建立「物体 → 所在位置」的准确映射（当前 `object_poses` 缺少 `parentReceptacles` 字段，多数 parent 靠动作序列推断），再回过头来加校验。

**当前处理**：在 `evalkit/simulator.py` 的 Pickup/Put 分支留了注释说明这个漏洞和修复失败的经过，避免后来者重复踩。

**使用建议**：引用任何与路径长度、步骤数相关的结论时，必须同时说明这个边界。

### 8. 约 1.6% 的 gold 序列存在标注不一致

抽检发现约 1.6% 的 gold 序列自身有问题。例如 `trial_T20190907_233445_502551`，任务描述是「get a knife to cut a tomato」，gold 只有拿起刀和切番茄两步，但 `pddl_params` 要求最终放到 SinkBasin，gold 根本没写 `PutObject`。

**处理方式**：这类样本会在 gold 验证中被识别出来（当前通过率 311/315 = 98.7%）。跑通率门槛（95%）就是用来兜住这类问题的。

## 六、防污染声明

- 评测集内容（问题与 gold 动作序列）**不出现在 prompt 模板的任何位置**
- prompt 模板见 `evalkit/models.py` 的 `PROMPT_SYSTEM` / `PROMPT_USER`，无 few-shot 样例
- 数据 hash 已记录在上方，可用于核查评测集是否被改动
- **本评测集不会用于训练任何模型**

**未做的事**：没有检查过 ALFRED 原始数据是否出现在各模型的预训练语料中。ALFRED 发布于 2020 年，被训练数据收录的可能性存在。这是本评测集无法排除的污染风险，引用结论时应说明。

## 七、复现方式

```bash
# 1. 下载数据（35.7MB，百度/亚马逊 S3 直链）
curl -o json_2.1.0.7z https://ai2-vision-alfred.s3-us-west-2.amazonaws.com/json_2.1.0.7z

# 2. 解压（不要用 py7zr，近两万个小文件会拖垮机器）
7z x json_2.1.0.7z

# 3. 抽样（固定 seed=42，可复现同样的评测集）
python scripts/import_alfred.py --root <解压目录>/json_2.1.0 --per-type 45 --limit-scan 8000

# 4. 验证状态机（必须过 95% 门槛）
python scripts/verify_gold.py

# 5. 查看统计
python scripts/dataset_stats.py
```

## 八、使用边界

**可以用来做**

- 评测模型把自然语言任务拆解成动作序列的能力
- 比较不同模型在具身高层规划上的表现
- 研究 LLM-as-a-Judge 在客观真值存在时的可靠性

**不能用来做**

- **推断机器人的真实执行成功率**。本评测只覆盖高层规划，不涉及抓取、力控、视觉反馈。规划成功不等于真机成功
- 评测 VLA 模型的端到端能力（不涉及动作预测精度）
- 泛化能力研究（`valid_unseen` 子集只有 12 条，样本不足）
