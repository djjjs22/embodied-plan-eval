# Judge 审计：结论与讲解框架

日期 2026-09-26
场景 embodied-plan-eval，315 条样本，Judge 用 DeepSeek-V4-Flash，真值来自符号状态机
用途 这份笔记的重点不是数据，是**怎么把这个结果讲给别人听**

---

## 一句话结论

**在具身任务规划上，LLM 能做「绝对判断」，不能做「相对判断」。**

绝对判断指「这条序列行不行」，Kappa 0.709，可用。
相对判断指「两条序列哪条更好」，翻转率 44.9%，和抛硬币无显著差异。

## 核心发现：Judge 有两副面孔

这份报告里最容易被问住的地方，是这两个数字**看起来矛盾**：

- 一致率 85.4%，听起来不错
- 翻转率 44.9%，听起来很差

同一把尺子怎么可能既准又不稳？

**因为它们测的是两种完全不同的能力。**

| | 绝对判断 | 相对判断 |
| --- | --- | --- |
| 任务形态 | 「这条序列能不能达成目标」 | 「A 和 B 哪条更好」 |
| Judge 要做的事 | 推演一条路径的最终状态 | 同时推演两条，再比较 |
| 认知负荷 | 一份 | 两份，且要维持不串 |
| 表现 | Kappa 0.709，可用 | 翻转率 44.9%，等同随机 |

**为什么相对判断会崩：** 模型要在一次推理里同时保持两条动作序列的状态（各自手上拿着什么、走到哪了），比只保持一条容易串。再加上模型本身有位置偏好，倾向选先出现的那个。

**关键证据是那个 50%。** 翻转率的随机基线是 50% —— 如果 Judge 闭着眼瞎选，正反两序指向同一条的概率恰好是一半。实测 44.9%，置信区间 [30.9%, 58.9%] 覆盖了 50%，p=0.48。**这不是「有点不稳」，这是「和抛硬币没有统计学差别」。**

（提醒：我第一次做这个判读时拿 0% 当基线，写成了「翻转率偏高，说明不够稳定」。那是错的。判读翻转率必须和 50% 比，因为随机情况下本来就会翻转一半。）

## 零术语版（讲给别人用这个）

第一版讲法里塞了六个术语（LLM-as-a-Judge、符号状态机、Cohen's Kappa、位置偏差、随机基线、p 值），
自己讲都费劲。**能讲明白的标志是：一个术语都不用。**

### 术语对照表

| 术语 | 讲给别人时这么说 |
| --- | --- |
| LLM-as-a-Judge | 让 AI 给 AI 打分 |
| 符号状态机 | 我写的一个小程序，能把动作序列真的跑一遍 |
| 客观真值 | 答案对不对不靠人评，跑一遍就知道 |
| Cohen's Kappa | 扣掉运气成分后的一致性 |
| 一致率 | AI 判的跟标准答案一样的比例 |
| 位置偏差 | 换个顺序问，答案就变了 |
| 随机基线 | 瞎猜的成绩 |
| p 值 | 这个结果有多大可能只是运气 |
| 放水率 | 做不到的被判成能做的 |
| 绝对判断 / 相对判断 | 单独看一条行不行 / 两条比哪个好 |

### 三步（零术语版）

**第一步，先给结论**

> 我做了个实验，结果挺反直觉的：让 AI 来判断另一个 AI 干得对不对，
> 它单独看一条能看准，但让它比较两条哪个好，它就基本在瞎猜了。

**第二步，说清楚怎么做的**

> 我写了个小程序，能把机器人的动作序列真的跑一遍，看最后有没有完成任务。
> 这个结果是死的，不靠人评也不靠 AI 评，就是标准答案。
>
> 然后我让 DeepSeek 在不看这个答案的前提下，自己判一遍同样 315 条。
> 两边的判断比对下来，一致性是 0.709。

**第三步，讲那个意外发现**

> 我还试了个变体：把两条序列换个顺序再问一遍。
> 结果换了顺序之后，接近一半的情况下它改口了。
>
> 而如果是纯瞎猜，改口率本来就在一半左右。
> 所以我这个 44.9% 说明，它在「比较两条哪个好」这件事上，跟抛硬币没区别。

## 讲解框架（术语版，方便自己核对细节）

给别人讲这个结果，按这个顺序，三步。

### 第一步，先给结论

> 我审计了 LLM-as-a-Judge 这把尺子。结论是它能做绝对判断，不能做相对判断。

**先说结论，不铺垫。** 背景部分（什么是具身规划、为什么不用仿真）等对方问了再讲。

### 第二步，说清楚怎么审的

> 我的项目里有个符号状态机，可以把动作序列真的「跑」一遍，用最终状态客观判定任务是否达成。这就是标准答案。
>
> 然后让 DeepSeek 做 Judge，在**看不到状态机结果**的前提下，对同一批 315 条样本独立判定一遍。两者对比，算 Cohen's Kappa。

这里有个词必须解释：**Kappa 不是一致率**。如果 55% 的样本本来就能达成，Judge 闭着眼全判「能」也有一致率 55%。Kappa 把这种「因为分布倾斜白得的一致」扣掉，剩下的才是真本事。所以 85.4% 的一致率对应 0.709 的 Kappa，而不是 0.854。

### 第三步，讲那个意外发现

> 我另外做了位置偏差实验：把模型序列和专家序列成对给 Judge，问哪条更好，正反两序各问一次。
>
> 结果翻转率 44.9%。而随机基线是 50%，统计检验 p=0.48 —— **它在这个任务上和抛硬币没有区别。**
>
> 所以我的结论是：Judge 单独判一条序列是可靠的（Kappa 0.709），但不要用它做两两比较。

### 被追问时怎么答

**问：Kappa 0.709 算好吗？**
> 超过 0.6 是业界常用的可信门槛，所以判「可用」。但它不是「很好」——0.8 以上才算接近完美。0.709 的含义是：如果项目里没有可执行的状态机，改用模型判定的可信度就是这个水平，能用于筛选，不适合用于最终决策。

**问：8.4% 的放水率意味着什么？**
> 12 条实际做不到的序列被判成了合格。这个方向比漏杀危险——漏杀只是低估了模型，放水会让不合格的规划通过审核，上线就是机器人真的去执行一个物理上做不到的动作。

**问：53.1% 的失败是「目标未达成」而不是前置条件违反，说明什么？**
> 说明模型的主要瓶颈是任务理解，不是物理常识。它知道东西拿了才能放，但经常放错地方或漏掉最后一步。改进方向是优化目标描述，不是补物理约束。

**问：这个结论能推广吗？**
> 在有客观真值的场景下可以。具身规划的好处是状态机可以执行验证；换成开放式生成任务，就没有标准答案，也就做不了这种审计了。这恰恰说明客观真值的价值。

## 工程建议

**要比较两个模型，不要用 pairwise 让 Judge 选哪个好，用各自的绝对判定再对比。**

理由就是上面的翻转率。让模型做两两比较，等于把结论建立在一个接近随机的判定上。

这也顺带解释了为什么 Chatbot Arena 那类 pairwise 排行榜的结果要谨慎看待 —— 它们依赖的正是模型最不擅长的那个能力。

---

## 局限（要主动说）

1. **只有一个被测模型**，自偏好实验做不了。等第二个模型跑过分才能补。
2. **位置偏差样本只有 49 条**，置信区间较宽（±14 个点）。结论方向可信，精确值不稳。
3. **Judge 只用了 DeepSeek-V4-Flash 一个**。换别的评判模型结论可能不同 —— 这本身值得再跑一次对比。
4. **只测了具身规划这一个任务域**。文本生成、代码生成上的表现未必一样。

## 数字复核（面试可能问怎么算的）

```
一致率 po = (138 + 131) / 315 = 0.854

期望一致率 pe = (150/315)(172/315) + (165/315)(143/315)
             = 0.4762 × 0.5460 + 0.5238 × 0.4539
             = 0.498

Kappa = (po - pe) / (1 - pe)
      = (0.854 - 0.498) / (1 - 0.498)
      = 0.709
```

其中 150 是 Judge 判「能」的总数（138+12），172 是真值判「能」的总数（138+34）。
