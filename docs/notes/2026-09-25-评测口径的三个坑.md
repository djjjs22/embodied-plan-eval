# 评测口径的三个坑

日期 2026-09-25
场景 embodied-plan-eval 首次全量跑（315 条，MiniMax-M3）
性质 实测踩坑记录，可迁移到任何评测项目

---

## 背景

第一次全量跑完，报告长这样：

| 指标 | 报告显示 |
| --- | --- |
| 任务成功率 | 40.0%（CI 35%-45%） |
| 前置条件违反率 | 17.1% |
| 序列精确匹配 | 0.0% |
| 失败构成 | ok 137 条占 72% |

第一眼看还算合理：分数不高，难度递减，符合预期。**但实际上三个指标全有问题。**

排查的入口是「失败构成里出现 ok 占 72%」这一行 —— 失败构成里不该出现 ok，这个矛盾点引出了全部三个坑。

**读评测报告的第一条纪律：找自相矛盾的地方。** 数字都能自圆其说时报告可信；一旦出现逻辑上不该出现的值，背后必然有代码问题。

---

## 坑一：API 失败没有从分母里剔除

### 现象

315 条里有 **79 条 API 失败**（占 25.1%），全部是 `RateLimitError 429` 触发限流。这些样本根本没拿到模型输出，却被当成「模型没做对」，算进了分母。

### 影响

同一个模型，两套口径差 13 个百分点：

| 口径 | 计算 | 结果 |
| --- | --- | --- |
| 全量作分母 | 126 / 315 | 40.0% |
| 剔除失败后 | 126 / 236 | **53.4%** |

### 为什么危险

40% 和 53.4% 是两个不同的结论。按 40% 写报告会得出「这个模型规划能力很弱」，而真实情况是「它过半能做对，只是评测跑挂了一批」。

面试官问「失败样本怎么处理的」，答不上来就说明没想过这个问题 —— 而它几乎是评测岗必问题，因为它直接决定分数可信度。

### 修法

1. 统计前先过滤：`valid = [s for s in scores if not s.error]`
2. 所有指标的分母统一用 `len(valid)`
3. **报告里显式写出剔除数量和占比**

第 3 点容易忽略但很重要：剔除要让人看见。悄悄剔除失败样本把分数做高，那不是评测是作弊。

### 根因

79 条全是限流，说明并发开太大（workers=8）。降到 3-4。失败的样本不写缓存，所以降低并发重跑会自动补齐 —— 第二次跑缓存命中 236 条，只补了缺的 79 条，没有重复花钱。

## 坑二：把「目标未达成」标成了「ok」

### 现象

失败构成里最大一类是 `ok`，137 条占 72%。这个标签的真实含义是：**所有动作都成功执行了，但最终目标条件没满足**。

代码里是这么写的：

```python
first_reason = next(
    (s.reason.value for s in steps if not s.ok), FailReason.OK.value
)
```

没有失败步骤时返回 `"ok"`。然后聚合时：

```python
counter[s.first_fail_reason or "目标未达成"] += 1
```

`"ok"` 是非空字符串，`or` 不触发，原样进表。

### 为什么危险

它把两种性质完全不同的失败混成一种：

| 失败性质 | 含义 | 改进方向 |
| --- | --- | --- |
| 前置条件违反 | 生成了物理上做不到的动作 | 补物理常识、加约束 |
| 目标未达成 | 动作都能做，但没做对 | 改任务理解、改规划策略 |

前者是「不知道手上有东西不能拿」，后者是「不知道最终要放到冰箱里」。解法完全不同，混在一起归因表就失效了。

### 修法

```python
r = s.first_fail_reason
counter["目标未达成（动作均可执行）" if r in ("", "ok") else r] += 1
```

## 坑三：格式污染让序列精确匹配恒为 0

### 现象

假过率 40%（后修正为 54.6%），但**序列精确匹配是 0.0%**，315 条一条都不匹配。

0% 和 100% 这种极端值通常说明指标本身坏了，不是模型真的差。

### 根因

抽一条看：

```
任务  move pillow from bed to chair
gold  ['GotoLocation(bed)', 'PickupObject(pillow)', 'GotoLocation(armchair)',
       'PutObject(pillow, armchair)', 'NoOp()']
输出  ['GotoLocation(bed)', 'PickupObject(Pillow)', 'GotoLocation(armchair)',
       'PutObject(Pillow, armchair)']
```

**模型这条完全正确。** 差异只有两处，都跟能力无关：

1. 大小写。gold 写 `pillow`，模型输出 `Pillow`
2. `NoOp()` 占位符。gold 序列末尾带它，模型不输出它 —— 而 **86% 的 gold 序列都含 NoOp**（270/315）

直接用字符串比较，这两条被判为不同。

### 影响

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 序列精确匹配 | 0.0% | 6.3% |
| 平均编辑距离 | 0.79 | 0.500 |

编辑距离受影响的原因是 gold 里的 NoOp 让序列凭空长一步，差异被放大。

### 修法

新增 `normalize_plan()`：转小写、丢掉 NoOp、参数排序（`(物体, 容器)` 和 `(容器, 物体)` 语义相同）。所有序列比较都走它。

### 但要认识到：修好了也只有 6.3%

**这个数字说明「精确匹配」作为指标本身区分度就弱。** 达成同一目标往往有多条等价路径，模型走的路和专家不同是正常的，不是错。

所以它只能当辅助指标。**主指标永远是「目标是否达成」，因为它不关心路径，只关心结果。**

这也解释了为什么还需要编辑距离（量化路径差多远）和 rubric（评路径质量）—— 三个指标各管一段，缺一不可。

## 修复后的完整结果

分母 = 315 条有效样本（第二次跑全部拿到输出）。

| 指标 | 值 | 95% CI |
| --- | --- | --- |
| 任务成功率 | 54.6% | [49.1%, 60.0%] |
| 前置条件违反率 | 21.9% | [17.7%, 26.8%] |
| 序列精确匹配 | 6.3% | [4.1%, 9.6%] |
| 平均编辑距离 | 0.500 | — |

**分层成功率**

| 难度 | 成功率 | 95% CI | n |
| --- | --- | --- | --- |
| L1 单步 | 77.8% | [68.2%, 85.1%] | 90 |
| L2 含状态改变 | 48.1% | [39.9%, 56.5%] | 135 |
| L3 多物体/容器 | 41.1% | [31.5%, 51.4%] | 90 |

L1 的区间下界 68.2% 高于 L2 的上界 56.5%，**区间不重叠**，说明难度分层有效，不是随机波动。这个证据比「数字递减」强得多。

**失败构成**（143 条失败）

| 原因 | 数量 | 占比 |
| --- | --- | --- |
| 目标未达成（动作均可执行） | 76 | 53.1% |
| 手上已有物体 | 23 | 16.1% |
| 手上不是该物体 | 18 | 12.6% |
| 物体不在场景中 | 8 | 5.6% |
| 该物体不可开关 | 7 | 4.9% |
| 容器不在场景中 | 6 | 4.2% |
| 位置不对 | 3 | 2.1% |
| 需要持刀才能切片 | 2 | 1.4% |

## 最有价值的结论

把失败按性质分两组：

- **任务理解类**：目标未达成 76 条，占失败 **53.1%**
- **物理常识类**：其余 67 条，占失败 **46.9%**

**M3 的主要瓶颈是任务理解，不是物理常识。** 它知道东西拿了才能放（违反率只有 21.9%），但经常放错地方或漏掉最后一步。

改进方向因此明确：优化 prompt 里的目标描述，而不是花力气补物理约束。

**这个结论只有在修掉坑二之后才可能得出来。** 如果那 76 条还叫「ok」，你看到的是「失败大头是个叫 ok 的东西」，得不出任何判断。**口径 bug 比模型 bug 更致命 —— 它会让你对着正确的结果得不出结论。**

---

## 可迁移的四条原则

**一、先定义分母，再算指标。** 任何百分比都要能回答「分母是什么」。评测里至少三层分母：全量样本、有效样本、判定通过的样本。混用会得出不同结论。

**二、剔除要显式写出来。** 剔除失败样本是必要的，但必须让读者看见剔除了多少、为什么剔。悄悄剔除等于造假。

**三、标签的默认值要单独设计。** 默认值往往在某条分支里被动产生，没人主动检查它，所以最容易出错。「无失败步骤」不等于「成功」，「无输出」不等于「失败」。

**四、极端值先怀疑指标，不要先怀疑被测对象。** 0% 和 100% 这种数字，优先去查指标实现有没有被无关因素污染。这次的锅是大小写和 NoOp，下次可能是空格或全半角标点。
