# 评测体系深度增强方案

版本 v1.0
日期 2026-09-26

---

## 一、先看清楚：浅在哪里

对照六个模块的现状：

| 模块 | 现状 | 浅在哪 |
| --- | --- | --- |
| 评估数据集 | 315 条，分层有效 | 缺覆盖度分析与偏差声明，别人不知道它的适用边界 |
| 评估指标 | 八张指标卡齐全 | 缺**指标间的印证**——每个指标单独报，没交叉验证 |
| 自动化 pipeline | 并发缓存报告齐全 | 缺回归门禁，改完代码不知道有没有倒退 |
| bad case | 8 类原因计数 | 只有计数，没有归因树、根因定位和回归闭环 |
| rubric | 四维度带锚点文档 | **文档写了从没跑过**，等于没有 |
| benchmark | 能出两模型对比 | 缺数据卡，无法对外发布 |

**诊断只有一个：都做到「有」就停了，没做校验。**

深度不来自把清单填满，来自**用已有的客观真值去验主观的东西**。这是这个项目独有的优势——绝大多数评测项目没有客观真值，只能把主观评分当结论。我们有，却没用起来。

## 二、深度增强：三项，全部能用现有数据

### A. rubric 校验（最重要）

**现在**：`rubric/plan_quality_v1.md` 四个维度写了锚点，零代码调用。

**深化**：让 Judge 按 rubric 给每条输出打分，然后**把主观分数和客观结果对照**。

具体要做三件事：

1. **主观 vs 客观的相关性**
   rubric 总分与「状态机判定是否达成」的相关系数。如果相关性高，说明这套 rubric 确实能反映真实质量；如果相关性低，说明 rubric 是摆设。

   这是整个项目最有价值的一个数字。因为它回答的是：**在没有客观真值的场景里，我们能不能用这套主观量表替代？**

2. **逐维度看判别力**
   四个维度分别算：达成目标的样本在该维度上的均分，对比没达成的。**哪个维度能区分好坏，哪个不能**。不能区分的维度要删掉或重设计——这是 rubric 迭代的正确方法，不是拍脑袋加维度。

3. **评分者间一致性**
   换一个模型当 Judge 再打一遍，算两个 Judge 之间的 Kappa。如果不同模型打分差很远，说明这套 rubric 的锚点还不够明确。

**成本**：一次 Judge 调用，315 条。做完之后 rubric 从「写了」变成「验证过的」。

---

### B. bad case 归因树与回归闭环

**现在**：报告里有一张失败原因计数表，8 类。

**深化成三层**：

**第一层，性质分类**（已有）
任务理解类 vs 物理常识类。现在能算：目标未达成 53.1%，其余 46.9%。

**第二层，根因定位**
不只说「手上已有物体」，要定位到**第几个动作、违反了哪条约束**。状态机已经记录了 `StepResult.index` 和 `FailReason`，信息全在，只是没往外输出。

示例输出：
```
第 3 步 PickupObject(Bread_1) —— 手上已有 Apple_1
根因：模型未执行放下动作就尝试拿取下一个物体
修复方向：prompt 中强化「一次只能手持一个」的约束提示
```

**第三层，回归集**
把 143 条失败样本存成 `dataset/regression.jsonl`，每条带归因标签。**这是闭环的关键**：改完 prompt 或状态机之后重跑这批用例，看同类错误有没有减少。没有这一步，评测就不能驱动改进，只是个打分器。

**成本**：零新增调用，纯代码整理。

---

### C. 数据卡与偏差分析

**现在**：没有。

**深化**：写 `docs/DATA_CARD.md`，但不只是罗列字段，要包含**用数据说话的偏差分析**：

| 内容 | 数据来源 |
| --- | --- |
| 规模与分层 | 315 条，L1 90 / L2 135 / L3 90 |
| 难度校准证据 | 分层区间不重叠（L1 下界 68.2% > L2 上界 56.5%） |
| 覆盖度 | 7 种任务类型、涉及的物体类型与容器类型分布 |
| 已知偏差 | ALFRED 场景均为室内家居；物体名带哈希后缀；86% 的 gold 序列含 NoOp 占位符 |
| 标注质量问题 | 约 1.6% 的 gold 序列自身存在标注不一致（如要求放置却未写 PutObject） |
| 防污染声明 | 评测集内容不出现在 prompt 模板中；数据版本 hash 记录 |
| 复现方式 | 下载直链 + 抽取命令 + 固定 seed |

**成本**：零调用，纯文档加统计。

## 三、广度增强：三项，按成本排序

| 项 | 做什么 | 成本 | 价值 |
| --- | --- | --- | --- |
| **valid_unseen 泛化子集** | 抽「训练中没见过的场景」跑一遍，看模型掉多少 | 一次评测调用 | 高。这个落差本身就是可报告的发现，且能证明评测集能测泛化 |
| **pass^k** | 每条跑 3 次，测稳定性 | 3 倍调用 | 中。能补上「可靠性」这一层指标，但花钱 |
| **第三个模型** | 再加一个被测模型 | 一次评测调用 | 中。多模型对比更有说服力，但不是必须 |

---

## 四、优先级建议

按「对面试含金量的贡献」排：

**第一梯队（必做，约两小时）**
1. **rubric 校验** —— 把「写了」变成「验证过的」，这是最锋利的一块
2. **bad case 回归集** —— 补上闭环，证明评测能驱动改进

**第二梯队（建议，纯文档）**
3. **数据卡** —— 开源和面试都用得上，且零调用成本

**第三梯队（可选）**
4. **valid_unseen 泛化对比** —— 一次调用，能出一个漂亮的落差数字
5. pass^k —— 花钱，时间够再做
6. CI 门禁 —— 锦上添花

**不要做**
- 不建议为了凑广度去加第五个第六个指标。**八个指标够用了，深度比数量重要。**

## 五、做完之后能讲什么

补完第一梯队，项目的叙述会变成这样：

> 我不只是建了个评测集。我用客观真值反过来校验了主观评分：rubric 的主观分数和真实达成情况的相关性是 X，说明这套量表能不能替代客观判定。我还发现模型的主要瓶颈是任务理解而非物理常识，并把 143 条失败沉淀成回归集，改动之后能验证同类错误有没有减少。

这段话里每一句都有数据支撑，每一句都经得起追问。**这才是「体系建设」该有的样子——不是一个清单，是一组互相印证的结论。**
