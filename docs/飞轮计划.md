# 飞轮计划：先想清楚为什么要建

日期 2026-09-29

---

## 一、先想清楚飞轮的目的

飞轮是闭合循环，目的是把「评测跑出来没用」变成「评测驱动改进」。

**写错版本**：迭代优化被测模型。**这是错的**——被测模型是别人家的 API，你改不了。

**正确版本**：迭代**评测体系自身**。具体产出三样：

1. 发现 gold 自身有问题的样本 → 修评测集
2. 发现归因标签不够细 → 修归因表
3. 发现状态机规则过严或过松 → 修规则

"改 prompt 让模型涨分"是副产品，可以做，但不该写在飞轮的目的栏里。

---

## 二、为什么分两轨

飞轮里有两种**性质完全不同的修复**，必须分开跑：

| 轨 | 修什么 | 验证什么 | 风险 |
| --- | --- | --- | --- |
| 模型轨 | prompt、few-shot | 跑回归集，看修复率 | 改坏 prompt 不会污染判定 |
| 状态机轨 | 状态机规则 | 跑 gold 通过率，必须 ≥ 95% | **改松规则直接让分数虚高** |

**混在一起的代价**：你以为模型能力提升了，其实是状态机放水了。这种错误我犯过——put 操作放松「必须先持有」的检查，通过率从 98.4% 升到 98.7%，当时还以为是修好了 bug。

所以两个轨必须分家，用两套不同的回归集、不同的报告、不同的修复方向。

---

## 三、飞轮骨架

```
┌──────────────┐
│  run_eval.py │  ← 跑全量评测
└──────┬───────┘
       ▼
┌──────────────────┐
│   归因（双轨）    │
│ ① 模型错误 → 回归集
│ ② 状态机 bug → 黄金集
└──────┬───────────┘
       ▼
┌──────────────────┐
│   修复（双轨）    │
│ ① 改 prompt / 加 few-shot
│ ② 改状态机规则
└──────┬───────────┘
       ▼
┌──────────────────┐
│   验证（双轨）    │
│ ① run_regression       ← 跑回归集
│ ② verify_gold          ← 跑黄金集
└──────┬───────────┘
       ▼
┌──────────────┐
│   diff 报告    │  ← 这轮修了什么 / 引入了什么新错
└──────┬───────────┘
       ▼
       └── 回到 run_eval
```

## 四、预算怎么分

预算 5000 次调用。建议这么分：

| 项目 | 调用次数 | 说明 |
| --- | --- | --- |
| 全量基线 | 945 | 315 条 × 3 模型（已有 1 跑，差 2 跑） |
| 子集多轮 | 900 | 从回归集抽 100 条 × 3 轮 × 3 模型 |
| 鲁棒性扰动 | 1575 | 315 × 5 扰动 |
| Rubric 校验 | 315 | Judge 给 315 条打分 |
| 回归复跑 | 250 | 双轨各 100 条 |
| Judge 自偏好 | 630 | 双向 × 300 |

**取舍**：

- **不做全量多轮**。945 × 3 = 2800 跑两轮没意义，子集抽 100 条跑三轮更有故事。
- **pass^k 只跑 50 条 × 3 轮 = 150**。稳定性指标了解个大概就行。
- **多轮交互不做**。缺 ground truth，做出来是半成品。

---

## 五、差了一个东西：归因自动打标

你提了三个待补的，我先做最重要的：**失败根因自动打标**。

**为什么这条最优先**：归因现在是 8 类固定标签，够粗。当 prompt 改完跑回归的时候，你需要知道"修好的是哪类、没修好的又是哪类、是否引入了新类"——细一级的归因才有这种信息。

**怎么实现**：用 Judge LLM 给每条失败输出一句话根因和修复建议，存进 `regression.jsonl` 的 `metadata` 字段。

**这是要花钱的**：315 次调用。可以跑 100 条先看效果，够用就行。

---

## 六、不做的事

- **不做 prompt 自动调优**。那是 LLM 优化，不是评测体系建设。
- **不做多轮交互**。缺 ground truth，做出来是半成品。
- **不做跨数据集**。边界已经够窄，再扩失焦。
- **不接 evalscope**。会丢差异化。
