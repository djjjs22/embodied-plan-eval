## 一、目标与边界

**目的**：让评测体系自身能迭代 —— 发现 gold 问题、修归因、修规则。
**不是**：优化被测模型（被测模型是别人的 API，你改不了权重）。

**总原则：双轨必须分家。**
回归集驱动 prompt 改进，golden 集驱动 simulator 修复。混在一起飞轮会自伤——
你以为是模型能力提升，其实是状态机放水。这条已经验证过了（路径多样性）。

```
│   ├── diff_flywheel.py         新建：对比两轮结果出报告
│   └── export_golden.py         新建：从 gold 提取状态机边界用例
├── reports/
│   ├── ... 已存在
│   ├── flywheel_round1.html
│   ├── flywheel_round2.html
│   └── flywheel_diff_v1_v2.html
└── docs/
    ├── ... 已存在
    └── flywheel_日志.md          新建：人读的工作记录
```

**为什么目录这么设计**：

- `regression_vN.jsonl` 永远不删，每次迭代是一份快照。diff 是「修了什么」的可信证据
- `golden.jsonl` 是状态机的边界用例，**不能从 regression 反推**。regression 是「模型能跑成什么样」，golden 是「状态机应该跑成什么样」——两者是相反方向的标尺
- `flywheel.py` 是入口脚本，**让飞轮可以一条命令跑完一轮**
- `flywheel_日志.md` 是人读的工作记录。**这是和「自动报告」并列的另一份产物**——给机器看的报告机器生成，给人看的日志人写

## 三、每个组件具体做什么

### 组件 1：Golden 集提取器

**做什么**：从 315 条评测集里，把那些「在 gold 验证里跑通、但本身是边界情况」的样本挑出来，做成 simulator 的回归基线。

**输入**：`dataset/cases.jsonl`
**输出**：`dataset/golden.jsonl`

**为什么需要它**：现在 `verify_gold.py` 跑出来 311/315 通过，那 4 条就是 simulator 的已知漏洞。把这 4 条固化下来，下次改 simulator 之前先跑它们，**别让「修一个漏洞引入另一个漏洞」的事故发生**。这是飞轮能转起来的基座。

**逻辑**：

1. 跑 `verify_gold.py` 拿所有失败样本
2. 把每条失败的根因（FailReason）和修复方向（来自 badcase.TAXONOMY）写进记录
3. 输出格式与 regression.jsonl 一致，但字段不同：标的是「**simulator 应该判失败**」，regression 标的是「**模型应该达成**」

**改/新文件**：`scripts/export_golden.py`（新建，约 80 行）

---

### 组件 2：飞轮主入口

**做什么**：一条命令 `python scripts/flywheel.py` 跑完一轮飞轮。

**输入**：当前评估集、golden 集、regression 集、被测模型配置
**输出**：

1. 在 `dataset/regression_v{N+1}.jsonl` 写下新一版的回归集（如果上轮没有就基于 v0 起步）
2. 跑 `run_regression.py` 拿本轮的回归通过率
3. 跑 `verify_gold.py` 拿状态机边界通过率
4. 跑 `run_eval.py --limit <回归子集>` 拿这一轮整体成功率
5. 调用根因打标器（组件 3）
6. 写 `reports/flywheel_round{N}.html`
7. 写 `docs/flywheel_日志.md` 的追加段

**为什么需要它**：现在每跑一轮要敲 4-5 个命令，记不住顺序。**入口脚本的价值不在于省事，在于「飞轮」这件事变成了一个可重复的流程**，新人接手也能跑。

**改/新文件**：`scripts/flywheel.py`（新建，约 200 行）

**关键设计**：

- **轮次号自动管理**：读 `dataset/regression_vN.jsonl` 找最大 N，新一轮就叫 N+1
- **所有 API 调用都在这一处**。子脚本接受 JSON 路径而不是直接调模型，方便单独跑某一步
- **失败不退出**。归因打标这一步可能调用失败，要继续把其他部分跑完，最后给出「这步失败的」清单

---

### 组件 3：根因自动打标器

**做什么**：让 Judge LLM 给 regression 集里每条失败输出「一句话根因 + 修复方向」，写到 metadata 字段。

**输入**：`dataset/regression_vN.jsonl` + Judge 模型
**输出**：更新后的 `dataset/regression_vN.jsonl`（每条多了 `judge_attribution` 字段）

**为什么需要它**：现在 8 类归因表（`evalkit/badcase.py` 的 TAXONOMY）太粗，251 条里有 76 条是「目标未达成」一类，原因五花八门。**自动打标能把这 76 条细分下去**，下一轮修复就有了更具体的方向。

**改/新文件**：`scripts/flywheel.py` 内一个函数 + `prompts/rootcause_system.md` + `prompts/rootcause_user.md`（新建）

**关键设计**：

- **根因长度限制在 30 字以内**。让 Judge 写一大段，分类难度会陡增
- **每个根因带一个 evidence 字段**：引用失败那一步的原文（来自 regression.jsonl 已有的 `attribution.step_text`）。这样人能快速判断「这个归因对不对」
- **调用成本**：251 条 × 1 次 ≈ 251 次。预算 5000 的话这一项就吃掉 5%

---

### 组件 4：Diff 报告生成器

**做什么**：对比 `regression_vN.jsonl` 和 `regression_v{N+1}.jsonl`，出三类信息：

1. **修了哪些**：`vN` 失败 `v{N+1}` 成功的样本，按根因分组
2. **引入哪些**：`vN` 成功 `v{N+1}` 失败的样本（**这才是飞轮危险的信号**）
3. **整体通过率变化**：从 a% 到 b%

**为什么需要它**：飞轮转起来之后，**最危险的不是修不好，是修了这条破坏了那条**。diff 报告显式标出"新引入的失败"——这就是回归。

**改/新文件**：`scripts/diff_flywheel.py`（新建，约 120 行）

**关键设计**：

- 「新引入的失败」单独用红色高亮。每轮 diff 报告都先看这一段
- 按根因分组统计。如果某类根因的「修了」数远多于「引入」数，说明那一类改得有效

---

### 组件 5：工作日志（人写的）

**做什么**：`docs/flywheel_日志.md`，每轮追加一段。

**格式**：

```markdown
## 第 N 轮（YYYY-MM-DD）

**目标**：本轮重点改的是「目标未达成」中的「最后一类」。
**改了什么**：prompt/plan_system.md 加了一段「目标条件复述」……
**修了**：regression 中 12 条从失败变成功
**引入**：3 条从成功变失败（都是 pick_two_obj_and_place，疑因新 prompt 干扰了两步规划）
**结论**：有效但有副作用。第 N+1 轮回退 prompt 的部分内容，只保留「目标复述」那段。
```

**为什么需要它**：

- HTML 报告给机器看，**日志给人看**。面试时讲飞轮，不能只甩数字，要能讲出「那一轮我在想什么、改了什么、为什么回退」——这就是工作日志存在的理由
- **也是飞轮的反思载体**。飞轮自伤最常见的原因就是「改了一条 prompt 同时改坏了别的事」，日志里要明确写「为什么改、怎么发现副作用、回退了什么」

**改/新文件**：`docs/flywheel_日志.md`（新建）

## 四、依赖关系与执行顺序

```
                  ┌──────────────────────┐
                  │ export_golden.py     │  一次性，跑出 golden.jsonl
                  └──────────┬───────────┘
                             │ 永久基座
                             ▼
                  ┌──────────────────────┐
                  │ flywheel.py round 1  │  跑出 regression_v1.jsonl + 第一轮报告
                  └──────────┬───────────┘
                             │ 你改 prompt 或 simulator
                             ▼
                  ┌──────────────────────┐
                  │ flywheel.py round 2  │  跑出 regression_v2.jsonl
                  └──────────┬───────────┘
                             │ 自动 diff
                             ▼
                  ┌──────────────────────┐
                  │ diff_flywheel.py     │  对比 v1 v2，出报告
                  └──────────────────────┘
```

**关键点**：每轮飞轮之间**必须有一个你改 prompt 或 simulator 的间隔**。否则就是「同一份数据跑两遍」，没意义。**飞轮的价值在于迭代，迭代的载体是「人做了什么改动」。**

## 六、收益与风险

### 收益

1. **有了动态数据**。「飞轮跑过 3 轮，回归通过率从 60% 到 78% 到 84%」——这个曲线比静态数据有说服力得多
2. **9 个脚本里唯一一个「闭环」类的**。前面 8 个都是「单次运行出数据」，飞轮是「多次迭代找规律」。**项目结构上多一类**
3. **能讲出「我是怎么修的」**。光有「我发现了问题」不够，还要有「我修过、证明有效、记录副作用」。飞轮就是干这个的

### 风险

1. **跑不起来**。如果飞轮脚本里某一步出 bug，会卡住整轮。**先在第 1 轮把骨架跑通**，别一上来就追求自动化
2. **引入比修的多**。prompt 改 A 可能影响 B，第 N+1 轮的「修了」比「引入」少，那一轮就是退步的。**diff 报告必须高亮引入部分**，每周看一次
3. **缓存把假象当真相**。你改了 prompt 但没升 `PROMPT_VERSION`，那 60% 的「修了」是缓存命中，假的。**每次改 prompt 必升版本号**

### 不该做的

- **不要把「优化被测模型」当飞轮目的**。被测模型是别人 API，你只能改 prompt，性质是「prompt 工程」不是「模型优化」
- **不要扩数据集**。扩了会改变飞轮的目标（你修的是「这一批样本上的问题」还是「这一类问题」就分不清了）
- **不要让飞轮全自动**。每轮之间必须有人工检查和决策，否则失控了都看不出来
