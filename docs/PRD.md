## 1 这个东西是什么

一个评测具身任务规划能力的工具。给模型一个家务任务描述和场景物体列表，让它输出动作序列，用符号状态机执行这条序列，按最终状态是否达成目标打分。

不用仿真器、不用 GPU、不用机器人。

---

## 2 目标与非目标

### 目标

| 编号 | 目标 | 验收 |
| --- | --- | --- |
| G1 | 建立可规模化的规划能力评测手段 | 单次全量评测可在 30 分钟内跑完，无需人工介入 |
| G2 | 判定标准客观，不依赖主观打分 | 主指标由代码判定，不经过任何模型 |
| G3 | 能定位失败原因，而不只报一个分数 | 失败用例自动归类，覆盖率不低于 80% |
| G4 | 结论可复现 | 同一份代码两次跑出同样的分数 |
| G5 | 产出可对外发布 | README 加数据卡完整，陌生人能按文档跑通 |

### 非目标

这几条比目标更重要，写在这里是为了防止中途范围蔓延。

| 不做 | 原因 |
| --- | --- |
| 不跑 3D 仿真 | 装 Docker 配 GPU 下几十 GB 场景资源，一周内做不完 |
| 不评测底层执行 | 抓取成功率和视觉误检需要真机或仿真，本项目不涉及 |
| 不训练或微调模型 | 被测对象是现成模型的 API，不是自己训的模型 |
| 不做分布式 | 315 条样本单机线程池足够，分布式是过度设计 |
| 不做 Web 界面 | 报告和 CLI 够用，界面不产生评测价值 |
| 不追求与官方榜单对齐 | 官方榜单已停用，且对齐需要提交流程，性价比低 |

## 3 需求清单

### 功能需求

**FR1 评测集构建**

从 ALFRED 抽取不少于 300 条样本，按 7 种官方任务类型分层，每种不少于 40 条。

验收：`cases.jsonl` 条数达标，L1/L2/L3 三层都有，字段完整。

**FR2 符号状态机**

实现 8 种高层动作的状态转移与前置条件校验，能逐条执行动作序列并检查最终状态。

验收：gold 序列跑通率不低于 95%。当前实测 311/315 = 98.7%。

**FR3 客观真值判定**

目标是否达成由 `pddl_params` 判定，逐子项检查，不经过模型。

验收：目标判定逻辑有单测覆盖，且能在报告中给出子项达成明细。

**FR4 模型接入**

支持通过配置切换被测模型，国内主流厂商走 OpenAI 兼容协议。

验收：改配置文件即可换模型，代码不用动。M3 需禁用 thinking 输出。

**FR5 指标体系**

产出任务成功率、子目标完成率、序列精确匹配、归一化编辑距离、前置条件违反率、pass^k、平均步数、调用成本。

pass^k 指同一条样本连续跑 k 次都成功才算通过，测的是稳定性而不是单次能力。pass@1 与 pass^k 的差值就是不稳定性。

验收：每个指标在 `docs/METRICS.md` 有定义、计算方式、口径、局限四段。所有百分比带置信区间。

**FR6 分层报告**

按任务类型和难度层分别出分，不能只有总分。

验收：报告含分层表格，每层样本数和置信区间可见。

**FR7 Bad case 归因**

失败用例自动归类到预定义的失败类型，输出归因分布和典型样例。

验收：失败样本归类覆盖率不低于 80%，归不了的标未分类不硬塞。

**FR8 Rubric 评分**

对状态机判不了的主观维度（绕路、冗余）用评分量表打��，含锚点样例和版本管理。

验收：`rubric/plan_quality_v1.md` 四个维度齐全，每档有锚点。版本号进 config，改版必须升号。

**FR9 Judge 可靠性审计**（Day 4 之后）

用状态机的客观判定当标准答案，审计 LLM-as-a-Judge 的一致率、Kappa、误判通过率，以及位置偏差。

验收：审计脚本可复现，四个数字都带置信区间。**这是整个项目方法论价值最高的一块。**

**FR10 回归门禁**

基线文件对比，掉分超过阈值阻断。

验收：人为破坏一条 gold，跑回归退出码非 0。

### 非功能需求

| 编号 | 需求 | 标准 |
| --- | --- | --- |
| NFR1 | 可复现 | temperature 固定 0，prompt 与 rubric 版本参与缓存键 |
| NFR2 | 成本控制 | 全量 315 条 × 3 模型 + Judge 审计，总成本控制在 200 元内（估算，按国内模型现价） |
| NFR3 | 缓存 | 重复调用命中缓存，中断后重跑不重复花钱 |
| NFR4 | 可解释 | 每个失败能指出是第几步、哪个动作、违反什么条件 |

## 5 方案要点

详细设计见 `README.md`、`docs/METRICS.md`、`rubric/plan_quality_v1.md`。这里只记三条不能动摇的原则。

**能用代码判的绝不交给模型。** 可执行性和目标达成由状态机判定，rubric 只评代码判不了的路径质量。这条贯穿所有设计决策。

**客观真值优先于主观评分。** 业界默认做法是用模型给模型打分，本项目反过来，先用可执行的客观真值，再用它去审计模型打分有多准。

**所有百分比带置信区间。** 315 条的区间约正负 5 个点，两个模型差距小于这个宽度就不能说谁更好。

| Day 6 | Judge 审计 + bad case 归因 | 四个数字 + 归因分布 | ✅ Kappa 0.709；251 条回归集 |
| Day 7 | 门禁 + 数据卡 + README | 陌生人能跑通 | ⚠️ 数据卡与门禁完成，README 待更新 |

**计划外多做的**

- **Judge 可靠性审计**：发现 Judge 能做绝对判断（Kappa 0.709）但不能做相对判断（翻转率 44.9%，与随机基线 50% 无显著差异）。这个结论比原计划的所有内容都硬
- **Rubric 校验**：逐维度分析主观评分的冗余与增量，回答「有客观真值时 rubric 还有没有用」
- **三个统计口径坑的修正**：API 失败未剔除（40% → 53.4%）、归因标签默认值（58 条失败被标成 ok）、格式污染（精确匹配恒为 0%）
- **多模型对比**：发现「越难差距越大」的模式（L1 差 4 点，L3 差 18 点），这个模式只有分层才能看出来

**仍未做的**

- pass^k 实跑（`scripts/run_passk.py` 已就绪，需 API 额度）
- valid_unseen 泛化对比（该子集当前仅 12 条，样本不足，需重新抽样）
- 第三个被测模型

## 7 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 状态机规则与 ALFRED 真实语义不符 | 误判，分数失真 | gold 验证门槛兜住，跑不通就修规则 |
| 只剩一个模型可用 | 自偏好实验做不了，Judge 审计结论偏乐观 | 至少再加一个便宜模型做跨族评判 |
| 高层成功不等于真机能执行 | 结论被误读 | 报告和简历里必须写明这个边界 |
| 一周做不完 FR9、FR10 | 方法论深度不足 | 优先保 FR7 归因，这两块可降级为文档 |

## 8 开放问题

1. 规模只测规划，是否需要在报告里给出一个"规划成功率到真机成功率"的折扣说明？倾向写，但要注明是估计不是实测。
2. pass^k 取 k=3 还是 k=5？取决于预算，先按 3 跑。
3. 是否需要 valid_unseen 子集做泛化对照？数据里有，成本允许就做，这个落差本身是个可报告的发现。
